# Findings: Kling AI's implicit "AI-generated" 

October 2026. All samples were generated by the author on two of their own Kling accounts through the normal website (kling.ai, international version). No sample files, real IDs or capture logs are published here; IDs below are made up but have the real shape.

For timed samples, the clock was read immediately before and after clicking Generate, giving a window of 0.45 to 11 seconds per sample.

## 2. Where the label lives

**PNG images:** a single `tEXt` chunk with keyword `AIGC`. There is no EXIF, XMP, C2PA or other metadata.

**MP4 video:** an Apple-style metadata box `moov/udta/meta` with an `mdta` key named `AIGC`. Its value is the same JSON as in images. The other keys are `major_brand`, `minor_version`, `compatible_brands` and `encoder`.

The JSON payload (made-up ID):

```json
{"Label":"1","ContentProducer":"kling","ProduceID":"SGP_PROD_ai_web_300000000123456","ReservedCode1":null,"ContentPropagator":"kling","PropagateID":"SGP_PROD_ai_web_300000000123456","ReservedCode2":null}
```

The field names match the implicit-metadata fields of China's GB 45438-2025 and the TC260 practice guides. In every sample, `Label` is `"1"` (AI-generated), `ProduceID` equals `PropagateID`, and `ContentProducer` equals `ContentPropagator`.

The video from 2025-07-24, made before the rules took effect on 2025-09-01, has no `AIGC` key. Its only metadata is an FFmpeg encoder tag.

## 3. `ProduceID` contains the creation time

Shape: `SGP_PROD_ai_web_` + 15 digits.

- The prefix was identical across both accounts, both image models and video. `SGP` most likely names the Singapore server cluster (Kling's download host also contains `sgp`); `PROD` is the production environment; `ai_web` is the website client. These readings are inferences.
- **Seconds counter (confirmed):** `floor(digits / 10^6)` is the number of seconds since **2016-07-09 01:41:59 UTC** (Unix time 1468028519).
  - Evidence: the five timed images give implied start times whose overlap is only 0.45 s wide (Unix 1468028518.78 to 1468028519.23). The timed video falls inside the same window.
  - Round 1 (no timing) agrees: across 24 images over 14 minutes, the counter rose 1.056 units per second of download time.
- **The last 6 digits = 3-digit worker + 3-digit milliseconds.**
  - **Milliseconds (strong evidence):** across 36 images, the last 3 digits of images from one batch fall within 15 of each other and rise in creation order. One four-image batch reads `.992`, `.994`, `.998` and then `.003` exactly as the seconds field ticks up by one. This is a millisecond rollover, not a wrapping counter.
  - **Worker (hypothesis):** the middle 3 digits differ for every image in a batch and took only values 300 to 318 and 500 to 527. Two pools of about 20 workers each fit this. The pool was not tied to model or account.
  - So the full creation time is `seconds.milliseconds`. With up to 2 s of server delay allowed after each click, the counter start lies between 2016-07-09 01:41:58.07 and 01:42:00.52 UTC (01:41:58.07 to 01:41:58.52 if there is no delay). Decoded times are accurate to about 1 second.

**Consequence:** anyone holding an original Kling file can read when it was generated, to the second:

```
created_utc = 1468028519 + floor(digits / 1_000_000)
```

> **Kling support disagrees on the wording (reply to the author's email, recorded 2026-10-15).** Kling support wrote that "the 15-digit payload contained in ProduceID/PropagateID does not include an exact timestamp." This does not match our measurements above: the decoded time fell inside the measured click window for 6 of 6 timed samples (2026-10-09), and the seconds field rises 1.056 units per second. We keep the finding, but it is best worded as **a time-derived counter that tracks the request time to about 1 second** (a custom epoch, not a Unix timestamp). The support answer is a short, non-technical reply, so it may mean "not a standard timestamp field". It is **not** a measurement. Cheap re-check: make one new image, note the clock time at the click, and run `kling-label` on it. If the decoded time is no longer within about 1 s, the scheme has changed.
>
> **Re-check from the repo, no new sample (2026-10-16).** The first four digits of an ID already place it on the calendar (1 unit of the seconds field = 1 s, so one prefix step = 27.8 h). The paid-plan batch of 2026-10-12 (generated 2026-10-11 to 10-12 per docs/dataset.md) has IDs starting `3237…`, which decodes to 2026-10-11 14:21 to 10-12 18:08 UTC: the right days. The earliest corpus (collected 2026-10-08 to 10-09; the old hygiene scan assumed prefix `3234`) decodes to 2026-10-08 03:01 to 10-09 06:48 UTC. The 2026-10-12 batch was not used to fit the epoch, so this tests the counter against the calendar over 3 days: it follows real time at about one unit per second, to within roughly 15%. That rules out a plain request counter. It does **not** re-measure the 1 s accuracy, which still rests on the 6 timed samples and the millisecond rollover. Only a fresh timed sample can do that.

The download URL served by Kling also embeds the `ProduceID` in base64, followed by further digits that were not analyzed.

## 4. Two formats of `ContentProducer`

| Account | Model | `ContentProducer` |
|---------|-------|-------------------|
| A | IMAGE 2.1 | `kling` |
| A | IMAGE 3.0 | `0011` + `91110108335469089C` + `10100` |
| B | IMAGE 2.1 | `kling` |
| B | VIDEO 3.0 | `kling` |
| B | IMAGE 3.0 | `0011` + `91110108335469089C` + `10100` |

The same account produced both formats, so **the model, not the account, decides the format**.

The 18-character middle part passes the check-digit algorithm of the Chinese **Unified Social Credit Code** (GB 32100-2015). It is the only 18-character window in the string that does. Its prefix `91` marks an enterprise, and `110108` is the administrative code for Haidian District, Beijing. **The code belongs to Beijing Kuaishou Technology Co., Ltd. (北京快手科技有限公司)**, Kling's developer, founded 2015-03-20. Search-engine indexes of two Chinese company-registry sites (Shuidi and Qichacha) list `91110108335469089C` as that company's taxpayer ID, together with organization code `33546908-9`. That organization code is embedded in the USCC itself (characters 9 to 17 = `335469089`), so the two identifiers agree. The registry sites themselves block visitors from outside mainland China, so this was confirmed through their indexed pages rather than the official GSXT registry. The `0011` prefix and `10100` suffix are presumably fields of the TC260 producer-code scheme; their meaning was not confirmed.

## 5. Pixel watermark: none found by our tests, but officially claimed (resolved in §9, 2026-10-12)

> **Update (2026-10-12):** paid-plan experiments (§9) strengthen this. A with/without-logo pixel diff and validated baked-in fixed-pattern tests (images and video) point the same way: **no independently detectable invisible watermark in the tested IMAGE 3.0 samples** — though these tests exclude *fixed / shared* marks, not a content-keyed or private-model mark, and Kling's own blind-watermark check is non-functional, so absence is not proven. The section below is the original 2026-10-09 evidence.

> **Update (Kling support reply, recorded 2026-10-15):** in reply to the author's inquiry, and "based on feedback from our relevant team", Kling support wrote: "Invisible image watermark: This feature is temporarily unsupported at the moment." This fits what we measured: the `BLIND_WATERMARK` check never returned a result, and no pixel test found a mark. It also means the public claim on kling.ai/docs/ai-content-detection (an imperceptible watermark in images and videos, retrieved 2026-10-09) does not describe the product today, at least for images. **Limits:** it is a second-hand support answer without technical detail; "this feature" could mean only the detector; it says nothing about video. So read it as *consistent with* "no invisible watermark in images today", not as proof.


Full method and numbers are in [notes/2026-10-09-pixel-spike.md](notes/2026-10-09-pixel-spike.md). Summary:

- **Noise-residual test (PRNU-style)** on 24 IMAGE 2.1 images: leave-one-out correlation averaged 0.0014, compared with 0.0000 for the 49 controls. A watermark designed for single-image detection would stand out far more.
- **Spectrum:** the only peaks are on a grid of multiples of 1/16 cycle per pixel (periods 2, 4, 8 and 16 px). This is typical of upscaling and VAE decoding, not a keyed carrier. No peaks were found off that grid.
- **Near-uniform images:** in one reference-mode image, 100% of interior pixels share a single red and green value (94). A pixel-domain watermark must change pixel values, so it has no room here. The two near-uniform images share only a ragged edge artifact about 32 px wide.
- **Least significant bits:** agreement between images was 0.506, which is what random bits give.
- **JPEG history:** Kling PNGs show no 8x8 blockiness, so they were not JPEG-compressed internally.

- **Near-uniform IMAGE 3.0 images (4):** interiors use only 1 to 3 values per channel; in one image green and blue are 100% a single value. Where two values occur, neighbouring pixels agree 93 to 99.7% of the time (smooth shading; a hidden ±1 pattern would give about 50%), and the two-value maps do not correlate consistently between images (-0.20 to +0.36, mixed signs). Plain text-to-image prompts on IMAGE 3.0 ignored "uniform grey" and drew portraits, so these were also made in reference mode.

- **105 near-uniform IMAGE 3.0 images (three accounts):** inside a 96 px margin, the median image uses only 2 values per channel (maximum 10), and in 48 of 105 images at least one channel is 100% a single value.
  - **No hidden shared pattern at watermark scales.** The averaged high-pass residual has energy 0.0094, matching pure noise for 105 images (1/105 = 0.0095).
  - **What the images do share is pipeline structure, not a keyed mark.** Split by spatial frequency, 93% of the shared signal is large-scale shading (periods above 200 px). Most of the rest is a faint grid with an exact 32 px period, which fits block- or tile-based generation followed by the 2x upscale (16 px at 1K becomes 32 px at 2K). A keyed watermark such as SynthID spreads pseudo-random energy over many frequencies; a single-period grid is not that.
  - **The grid cannot identify Kling images.** In single images, the 32 px spectral peak was no higher for Kling (median ratio 1.9 for plain, 4.3 for normal IMAGE 3.0) than for the 49 non-Kling controls (median 7.7, mostly screenshot and JPEG block structure).

**Off-the-shelf watermark detectors** (each checked with a positive control first):

| Detector | Kling images flagged | Positive control |
|----------|----------------------|------------------|
| Google SynthID Detector (synthid.com, 1 image) | 0/1, "SynthID was not detected" | n/a (Kling is not a SynthID partner) |
| Stable Diffusion `invisible-watermark` (dwtDct) | 0/14, decodes to all-0 or all-1 bits | n/a |
| Adobe TrustMark, variants Q and P | 0/36 each | Detected and decoded |
| Meta Watermark Anything (`wam_mit`) | 0/36 (max 8% of pixels, below the 10% threshold) | 100% of pixels detected |

A third-party "AI image detector" website rated a Kling image 99% AI. Such sites are classifiers that judge how an image looks; they do not read watermarks, so this does not indicate a hidden mark.

**Official claim (added after the tests above):** Kling's [AI Content Detection](https://kling.ai/docs/ai-content-detection) page states that "an imperceptible watermark and metadata are embedded in images and videos" and stay traceable "through compression, editing, and resharing". Its detector (kling.ai/detection) runs two checks, `AIGC_METADATA` and `BLIND_WATERMARK`. On 2026-10-09 every image submission (including an untouched original) returned `FAILED` for both checks; the VIDEO 3.0 file returned metadata `Detected` and blind watermark `FAILED`.

**Consequence:** the `AIGC` metadata is the only label we could verify in images. Our tests rule out common schemes and any mark in flat regions, but not a keyed mark embedded only in textured regions, so whether pixels alone identify a Kling image remains open. See [docs/forensic-audit-2026-10-09.md](docs/forensic-audit-2026-10-09.md).

**Video bitstream marker:** the VIDEO 3.0 file also contains one H.264 SEI `user_data_unregistered` message (UUID `91ca6061-4aee-3854-8614-2d5f73f4ae2e`, payload `kling-ai`) inside the coded video. The 2025 video has none.

## 8. Official detector behaviour and further tests (2026-10-09, later)

- **Kling's detector does not recognise IMAGE 3.0 labels.** Its `AIGC_METADATA` check returned `DETECTED` for files whose producer is `kling` (IMAGE 2.1 original, Inpaint output) and `NOT_DETECTED` for 2 of 2 untouched IMAGE 3.0 originals, whose producer is the USCC form. JPEG copies return `UNSUPPORTED`.
- **The `BLIND_WATERMARK` check never produced a result:** `FAILED` on all 15 image submissions and the video, including tasks that otherwise completed.
- **Edit tools regenerate everything.** Kling Inpaint and Expand, run on our own test image, re-create the whole image at 1024x1344, so a "same edit twice" comparison cannot isolate a watermark. In flat regions, three of four Inpaint outputs were nearly identical (about 1% of pixels differ), so no per-output code is added to flat areas.
- **Second video:** a VIDEO 3.0 Omni clip (May 2026, downloaded as MOV) carries the same `kling-ai` H.264 SEI marker but no `AIGC` container key. The SEI marker is present in 2 of 2 post-rules videos.
- **Second-order (payload) test, 54 textured IMAGE 3.0 images:** no shared fixed pattern (z = +0.1); a small excess in pairwise correlation spread (+11.8%, z = +3.0). The same test on non-Kling control photos (which include burst shots and screenshots) shows a far larger excess, so the method reacts strongly to shared layout and content. The Kling excess is therefore not evidence of a watermark.

- **Latent-noise test (Colab, public Stable Diffusion 1.5 inversion):** a self-made Tree-Ring-style positive control was detected (p = 0.0011), while 40 Kling IMAGE 3.0 images scored like clean images (p = 0.57). No generation-time ring watermark is visible through a public model; a mark readable only with Kling's own model remains possible. Details: docs/watermark-hunt-results-2026-10-09.md.

## 9. Paid-plan experiments (2026-10-12): the watermark question, resolved

Run on a paid Standard plan (IMAGE 3.0, 2K HD), driving the real web app. Detection only; the "without watermark" files were made by Kling's own download option. Full method and numbers: [docs/paid-credits-experiment-2026-10-12.md](docs/paid-credits-experiment-2026-10-12.md).

- **Same image, with vs without the visible logo (Test A).** We obtained both versions of one generated image. They are **byte-identical outside the logo corner** (centre 1024x1024 identical; 99.8% of all pixels identical; 0.000% differ outside the corner). The "Without Watermark" step changes **only the ~8,000 pixels of the visible "KlingAI 3.0" corner logo** and nothing else. So **no invisible pixel watermark is added in the finishing step** — this disproves the API hypothesis (`watermark_info` → `watermark_url`). The `AIGC` metadata is present in both versions.
- **Kling's own detector, reproducibility matrix (Test B).** On a pristine without-logo IMAGE 3.0 PNG the detector returned "No supported signal" (`AIGC metadata: Not detected`, `Invisible watermark: Failed`) while our `kling-label` reads the `AIGC` label (USCC form) in the same file — the IMAGE 3.0 metadata gap, live. **But `Failed` is not `NOT_DETECTED`.** Re-running the matrix: a VIDEO 3.0 original (producer `kling`) returned `AIGC metadata: Detected` yet `Invisible watermark: Failed` — the blind-watermark check fails even on a file positively identified as Kling. And on 2026-10-12 **every image upload** returned the service error "Detection failed. Please try again" (7/7; video worked 2/2), so image detection was simply down. The honest reading: the metadata check works and exposes the IMAGE 3.0 gap, but the blind-watermark check is **non-functional** and gives no evidence either way about an invisible watermark. Test B therefore does **not** support "no watermark"; that rests on Tests A, C, D and the earlier forensics.
- **Baked-in fixed-pattern test across 3 different scenes (Test C).** Pairwise high-pass residual correlation (full frame minus corner, ~3.9M px). Real images: z = **+0.1** vs the shuffled null (no shared pattern). Positive controls planted into these same images: ±1 level → z = +13.7, ±2 → z = +58.4 (both DETECTED). So the test would catch any fixed baked-in mark of ±1 level or stronger; Kling shows none.
- **Video frames (Test D).** Temporal-average residual correlation across 3 different Kling videos (steam, Omni, a freshly generated city clip) is 0.005 — the same as unrelated control videos (0.004) — while a planted ±2 positive control gives 0.045. So no shared frame watermark; the only video markers remain the `kling-ai` H.264 SEI and the `AIGC` metadata. (One sample pair turned out to be the same file, MD5-identical, caught by an r = 1.000; a fresh video was generated to keep three distinct clips.)
- **Edit / Expand pipeline, metadata preservation.** All 6 Inpaint/Expand outputs **keep** the `AIGC` label, but with producer **`kling`** (not the IMAGE 3.0 USCC form of their inputs), regenerated at 1024x1344. So editing preserves the label *and* changes its producer form — which means an edited IMAGE 3.0 image is **more** detectable by Kling's own detector (it reads `kling`) than the untouched IMAGE 3.0 original (USCC, which the detector misses). Metadata survives this workflow; the detector gap does not.
- **Large-scale averaging (#4) and blind-watermark decode (#5) — both negative after a content control.** Averaging the residuals of 331 IMAGE 3.0 images, and decoding them with the open `blind_watermark` library (DWT-DCT-SVD, the same family as Kling's `BLIND_WATERMARK` check), both first produced Kling-specific-looking signals (averaging 2.6–4.4× the noise floor, split-half r = 0.41; decode agreement 0.64 vs 0.50 for non-Kling). Both vanished under the decisive control — comparing Kling images that share **no content**: cross-batch residual correlation round4×round5 = −0.001, and cross-batch decode agreement round4×round5 = 0.49 (round4×a fresh session = 0.50). So both were artifacts of repeated prompts / near-duplicate batches (round3 ≈ round4, r = 0.986), not a watermark. This lowers the excluded *fixed*-mark floor to ≈ ±0.24 levels (methodology.md). A clean ground-truth test remains available via the API (`forensics/api_watermark_diff.py`).
- **Learn-a-detector (#2) — no reliable pixel signature.** A RandomForest on high-pass residual spectra separates round4 Kling from Gemini with in-sample 5-fold AUC = 1.000, but on content-different held-out data (round5 + fresh paid images) it drops to AUC 0.59 (scale-normalised) / 0.72 (native) and scores every held-out Kling image as non-Kling. The in-sample 1.0 was content/batch overfitting; the faint native-resolution tendency fits the known 2× upscale fingerprint (§5), not a deliberate content-keyed watermark. This is the one method that could catch a *keyed* mark — and it finds no usable one. Script: `forensics/pixel_classifier.py`.
- **New detail on `ProduceID`:** it is **per generation batch** — both images in a 2-image request share the same `ProduceID` and timestamp, so the ID identifies the request, not the single image.

**Bottom line.** No **independently detectable** invisible watermark was found in the tested IMAGE 3.0 samples (or, from Test D, their video frames), across our own methods — each with a positive control. The markings we *can* confirm are the visible corner logo (easily removed) and the `AIGC` text metadata (which Kling's own detector cannot read for IMAGE 3.0). This is not proof of absence: these tests target *fixed / shared* patterns, so a content-keyed mark, or one readable only with Kling's private model, is not excluded (and Kling's own blind-watermark check is non-functional, so it cannot settle the question). Such a mark would, however, have to survive ordinary compression to provide the traceability Kling claims. The more defensible finding is the **detector gap** itself: Kling's tool misreads its own IMAGE 3.0 metadata and its blind-watermark check never returns a result.

## 11. Ethics

This work is detection-only. It reads and explains a label; it does not provide tools or steps to remove, forge or alter labels, and doing so may violate the labeling rules and Kling's terms. Only the author's own generations were analyzed.
