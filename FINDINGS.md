# Findings: Kling AI's implicit "AI-generated" label

October 2026. All samples were generated by the author on two of their own Kling accounts through the normal website (kling.ai, international version). No sample files, real IDs or capture logs are published here; IDs below are made up but have the real shape.

## 1. Data

| Set | Account | Model | Count | Notes |
|-----|---------|-------|-------|-------|
| Round 1 | A | IMAGE 2.1 | 24 + 2 | 2K 9:16 text-to-image; 2 near-uniform images from reference mode |
| Round 2 | B | IMAGE 3.0 | 5 | 3 timed 2K 9:16, 1 timed 1K 9:16, 1 timed 2K 1:1 |
| Round 2 | B | IMAGE 2.1 | 1 | Same prompt as an IMAGE 3.0 image, to separate model from account |
| Round 2 | B | IMAGE 3.0 | 4 | Near-uniform grey, 2K 9:16, made with a flat reference image |
| Round 2 | B | VIDEO 3.0 | 1 | 720p, 3 s, timed, downloaded as MP4 |
| Round 2 | B | VIDEO 1.5 | 1 | Generated 2025-07-24, before the labeling rules took effect |
| Control | - | - | 49 | Non-Kling photos, screenshots and downloaded images |

For timed samples, the clock was read immediately before and after clicking Generate, giving a window of 0.45 to 11 seconds per sample.

## 2. Where the label lives

**PNG images:** a single `tEXt` chunk with keyword `AIGC`. There is no EXIF, XMP, C2PA or other metadata.

**MP4 video:** an Apple-style metadata box `moov/udta/meta` with an `mdta` key named `AIGC`. Its value is the same JSON as in images. The other keys are `major_brand`, `minor_version`, `compatible_brands` and `encoder`.

The JSON payload (made-up ID):

```json
{"Label":"1","ContentProducer":"kling","ProduceID":"SGP_PROD_ai_web_300000000123456","ReservedCode1":null,"ContentPropagator":"kling","PropagateID":"SGP_PROD_ai_web_300000000123456","ReservedCode2":null}
```

The field names match the implicit-metadata fields of China's GB 45438-2025 and the TC260 practice guides. In every sample, `Label` is `"1"` (AI-generated), `ProduceID` equals `PropagateID`, and `ContentProducer` equals `ContentPropagator`.

The video from 2025-07-24, made before the rules took effect on 2025-09-01, has no `AIGC` key. Its only metadata is an FFmpeg encoder tag.

## 3. `ProduceID` contains the creation time

Shape: `SGP_PROD_ai_web_` + 15 digits.

- The prefix was identical across both accounts, both image models and video. `SGP` most likely names the Singapore server cluster (Kling's download host also contains `sgp`); `PROD` is the production environment; `ai_web` is the website client. These readings are inferences.
- **Seconds counter (confirmed):** `floor(digits / 10^6)` is the number of seconds since **2016-07-09 01:41:59 UTC** (Unix time 1468028519).
  - Evidence: the five timed images give implied start times whose overlap is only 0.45 s wide (Unix 1468028518.78 to 1468028519.23). The timed video falls inside the same window.
  - Round 1 (no timing) agrees: across 24 images over 14 minutes, the counter rose 1.056 units per second of download time.
- **The last 6 digits = 3-digit worker + 3-digit milliseconds.**
  - **Milliseconds (strong evidence):** across 36 images, the last 3 digits of images from one batch fall within 15 of each other and rise in creation order. One four-image batch reads `.992`, `.994`, `.998` and then `.003` exactly as the seconds field ticks up by one. This is a millisecond rollover, not a wrapping counter.
  - **Worker (hypothesis):** the middle 3 digits differ for every image in a batch and took only values 300 to 318 and 500 to 527. Two pools of about 20 workers each fit this. The pool was not tied to model or account.
  - So the full creation time is `seconds.milliseconds`. With up to 2 s of server delay allowed after each click, the counter start lies between 2016-07-09 01:41:58.07 and 01:42:00.52 UTC (01:41:58.07 to 01:41:58.52 if there is no delay). Decoded times are accurate to about 1 second.

**Consequence:** anyone holding an original Kling file can read when it was generated, to the second:

```
created_utc = 1468028519 + floor(digits / 1_000_000)
```

The download URL served by Kling also embeds the `ProduceID` in base64, followed by further digits that were not analyzed.

## 4. Two formats of `ContentProducer`

| Account | Model | `ContentProducer` |
|---------|-------|-------------------|
| A | IMAGE 2.1 | `kling` |
| B | IMAGE 2.1 | `kling` |
| B | VIDEO 3.0 | `kling` |
| B | IMAGE 3.0 | `0011` + `91110108335469089C` + `10100` |

The same account produced both formats, so **the model, not the account, decides the format**.

The 18-character middle part passes the check-digit algorithm of the Chinese **Unified Social Credit Code** (GB 32100-2015). It is the only 18-character window in the string that does. Its prefix `91` marks an enterprise, and `110108` is the administrative code for Haidian District, Beijing. **The code belongs to Beijing Kuaishou Technology Co., Ltd. (北京快手科技有限公司)**, Kling's developer, founded 2015-03-20. Search-engine indexes of two Chinese company-registry sites (Shuidi and Qichacha) list `91110108335469089C` as that company's taxpayer ID, together with organization code `33546908-9`. That organization code is embedded in the USCC itself (characters 9 to 17 = `335469089`), so the two identifiers agree. The registry sites themselves block visitors from outside mainland China, so this was confirmed through their indexed pages rather than the official GSXT registry. The `0011` prefix and `10100` suffix are presumably fields of the TC260 producer-code scheme; their meaning was not confirmed.

## 5. No invisible pixel watermark

Full method and numbers are in [notes/2026-10-09-pixel-spike.md](notes/2026-10-09-pixel-spike.md). Summary:

- **Noise-residual test (PRNU-style)** on 24 IMAGE 2.1 images: leave-one-out correlation averaged 0.0014, compared with 0.0000 for the 49 controls. A watermark designed for single-image detection would stand out far more.
- **Spectrum:** the only peaks are on a grid of multiples of 1/16 cycle per pixel (periods 2, 4, 8 and 16 px). This is typical of upscaling and VAE decoding, not a keyed carrier. No peaks were found off that grid.
- **Near-uniform images:** in one reference-mode image, 100% of interior pixels share a single red and green value (94). A pixel-domain watermark must change pixel values, so it has no room here. The two near-uniform images share only a ragged edge artifact about 32 px wide.
- **Least significant bits:** agreement between images was 0.506, which is what random bits give.
- **JPEG history:** Kling PNGs show no 8x8 blockiness, so they were not JPEG-compressed internally.

- **Near-uniform IMAGE 3.0 images (4):** interiors use only 1 to 3 values per channel; in one image green and blue are 100% a single value. Where two values occur, neighbouring pixels agree 93 to 99.7% of the time (smooth shading; a hidden ±1 pattern would give about 50%), and the two-value maps do not correlate consistently between images (-0.20 to +0.36, mixed signs). Plain text-to-image prompts on IMAGE 3.0 ignored "uniform grey" and drew portraits, so these were also made in reference mode.

**Off-the-shelf watermark detectors** (each checked with a positive control first):

| Detector | Kling images flagged | Positive control |
|----------|----------------------|------------------|
| Google SynthID Detector (synthid.com, 1 image) | 0/1, "SynthID was not detected" | n/a (Kling is not a SynthID partner) |
| Stable Diffusion `invisible-watermark` (dwtDct) | 0/14, decodes to all-0 or all-1 bits | n/a |
| Adobe TrustMark, variants Q and P | 0/36 each | Detected and decoded |
| Meta Watermark Anything (`wam_mit`) | 0/36 (max 8% of pixels, below the 10% threshold) | 100% of pixels detected |

A third-party "AI image detector" website rated a Kling image 99% AI. Such sites are classifiers that judge how an image looks; they do not read watermarks, so this does not indicate a hidden mark.

**Consequence:** the `AIGC` metadata is the only machine-readable label. Any screenshot, re-encode or metadata-stripping upload removes it, and the file then carries no trace of the label. This is a property of the labeling design, not a removal method.

## 6. Image sizes and upscaling

| Setting | Size |
|---------|------|
| 1K, 9:16 | 768 x 1360 |
| 2K, 9:16 | 1536 x 2720 |
| 2K, 1:1 | 2048 x 2048 |

2K is exactly twice 1K, which suggests the 2K output is a 2x upscale. This matches the period-2 grid in the spectrum. A plain-white 2K image also shows tile seams consistent with tiled upscaling.

## 7. Tool validation on real files

`kling-label` v0.1 was built in a cloud session using only synthetic test files, then run locally on the real samples:

| Input | Result |
|-------|--------|
| 36 Kling PNGs (IMAGE 2.1 and 3.0, two accounts) | 36/36 label found |
| New VIDEO 3.0 MP4 | label found (`moov/udta/meta`) |
| VIDEO 1.5 MP4 from before the rules | correctly reported as no label |
| 49 non-Kling control files (25 JPEG, 24 PNG) | 0/49 false positives |
| 6 timed samples | every decoded creation time fell inside its measured click window (within 1 s) |

## 9. Ethics

This work is detection-only. It reads and explains a label; it does not provide tools or steps to remove, forge or alter labels, and doing so may violate the labeling rules and Kling's terms. Only the author's own generations were analyzed.
